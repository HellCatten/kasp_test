Локальный отказоустойчивый контур мониторинга для Uptime Kuma
Контекст
Вам предстоит построить локальный контур мониторинга для продакшн-сервиса Uptime Kuma. Вся инфраструктура разворачивается локально, а жизненным циклом и конфигурацией управляет Dagger.
Использование AI-ассистентов не ограничено — но архитектурная целостность, безопасность и работоспособность итогового решения остаются зоной ответственности кандидата.

1.	Системные требования
ОС: Linux, macOS или Windows 10/11 (через WSL с установленным Docker Desktop / Docker Engine)
Стек: Docker, Docker Compose, Dagger CLI, MariaDB, Prometheus, Grafana, Uptime Kuma

2.	Архитектура решения
Стенд состоит из двух независимых слоёв (docker-compose).
Слой 1 — Приложение и БД
•	Uptime Kuma — сервис в контейнере (см. https://github.com/louislam/uptime-kuma )
•	MariaDB — одна нода, БД для Uptime Kuma, данные сохраняются при перезапуске (volume)
Слой 2 — Наблюдаемость
•	Prometheus — сбор метрик: состояние контейнеров и хоста, доступность и latency веб-сервисов (конкретные экспортёры — на ваше усмотрение)
•	Grafana — дашборд здоровья контура: CPU/RAM и прочие ресурсы контейнеров, статус БД MariaDB, статус сервиса Uptime Kuma

3.	Требования к автоматизации (Dagger.io)
В корне репозитория должен находиться Dagger-модуль (рекомендуется выбрать Go, но также можно Python или TypeScript SDK). Dagger управляет хостовым Docker-демоном через проброс сокета `/var/run/docker.sock` (см. https://docs.dagger.io/extending/arguments#unix-sockets ).
Необходимо реализовать 3 команды:
•	`dagger call deploy-app` — Поднимает MariaDB и Uptime Kuma, связывает их
•	`dagger call deploy-monitoring` — Поднимает стек Prometheus и Grafana
•	`dagger call configure-grafana` — Через Grafana API накатывает Data Sources, дашборды

4.	Бонусные задачи
•	End-to-End Orchestration (`dagger call deploy-all`) — команда поднимает всю платформу целиком и валидирует статус всех систем.
•	Chaos Testing — скрипт или команда Dagger, останавливающая контейнер MariaDB или Uptime Kuma (`docker stop`), с проверкой, что: 
o	(а) на Grafana дашборде виден переход в статус Все Плохо
o	(б) сервис поднимается обратно (restart-policy) и дашборд отражает восстановление.
•	Galera Cluster — реализация кластера MariaDB (Galera) вместо одиночной ноды. В этом случае необходимо использовать 3 ноды MariaDB + HAProxy.
