## 2. Примеры некорректных, устаревших и неоптимальных решений AI

Ниже приведены 5 ключевых кейсов, когда рекомендации ИИ привели к сбоям или архитектурному долгу, а также описание того, как проблемы были локализованы и устранены.

---

### Кейс 1. Устаревший скрипт Healthcheck MariaDB и ошибка в переменной окружения Uptime Kuma

* **Что предложил ИИ:**  
  В блоке `healthcheck` контейнера MariaDB поисковый ИИ выдал:
  ```yaml
  test: ["CMD", "healthcheck.pl", "--connect", "--innodb_initialized"]
  ```
  А в переменных окружения сервиса Uptime Kuma указал:
  ```yaml
  UPTIME_KUMA_DB_USER: uptime
  ```
* **Как обнаружена проблема:**  
  1. Контейнер MariaDB бесконечно находился в статусе `unhealthy` и блокировал запуск зависимых сервисов (`depends_on: condition: service_healthy`). В логах отображалась ошибка отсутствия скрипта `healthcheck.pl`.
  2. Uptime Kuma не могла подключиться к базе данных и падала с ошибкой авторизации (переменная с логином пользователя игнорировалась).
* **Причина ошибки ИИ:**  
  Галлюцинация на базе устаревших версий образов: в современных образах MariaDB скрипт проверки написан на Shell (`.sh`), а не на Perl (`.pl`). В образе Uptime Kuma имя переменной строго `UPTIME_KUMA_DB_USERNAME`, а не `_USER`.
* **Исправление:**  
  Сверено с [официальной документацией MariaDB](https://mariadb.com/docs/server/server-management/automated-mariadb-deployment-and-administration/docker-and-mariadb/using-healthcheck-sh/) и репозиторием [Uptime Kuma Wiki](https://github.com/louislam/uptime-kuma/wiki/Environment-Variables). Параметры исправлены на:
  * `healthcheck.sh` вместо `healthcheck.pl`.
  * `UPTIME_KUMA_DB_USERNAME=uptime`.

### Кейс 2. Устаревший синтаксис подключения `mysqld-exporter` (DATA_SOURCE_NAME)

* **Что предложил ИИ:**  
  Для сбора метрик с MariaDB ИИ сгенерировал передачу строки подключения через переменную окружения:
  ```yaml
  environment:
    DATA_SOURCE_NAME: "root:rootsecretpassword@(mariadb:3306)/"
  ```
* **Как обнаружена проблема:**  
  Экспортер циклически перезапускался с ошибкой:
  `msg="failed to validate config" section=client err="no user specified in section or parent"`  
  `msg="Error parsing host config" file=.my.cnf err="no configuration found"`
* **Причина ошибки ИИ:**  
  Начиная с версии `mysqld_exporter v0.15.0+`, механизм аутентификации через `DATA_SOURCE_NAME` был признан устаревшим (deprecated), и экспортер принудительно стал требовать конфигурационный файл формата `.my.cnf` с валидной секцией `[client]`. ИИ обучался на тысячах старых примеров и не учел изменения в мажорных версиях утилиты.
* **Исправление:**  
  Создан выделенный файл конфигурации `.my.cnf` с правами `chmod 600`, смонтирован в `/etc/.my.cnf:ro`, а экспортер переведен на флаг запуска `--config.my-cnf=/etc/.my.cnf`. Это также повысило безопасность (пароль перестал светиться в `docker inspect`).

### Кейс 3. Архитектурный антипаттерн «String-in-String Hell» в Dagger-модуле

* **Что предложил ИИ:**  
  Для выполнения команд настройки Uptime Kuma и Grafana API внутри Dagger ИИ сгенерировал код на Go, где скрипты Node.js и сложные многострочные JSON-пейлоады для `curl` были захардкожены в виде гигантских строковых констант:
  ```go
  // Антипаттерн, предложенный ИИ:
  importDashboardCmd := []string{
		"sh", "-c",
		`PAYLOAD=$(cat /dashboards/health-dashboard.json) && \
		curl -s -f -X POST \
		-H "Content-Type: application/json" \
		-d "{\"dashboard\": $PAYLOAD, \"overwrite\": true}" \
		http://admin:admin@grafana:3000/api/dashboards/db`,
	}
  ```
* **Как обнаружена проблема:**  
  Невооруженным глазом виден бойлерплейт строк, который съедал много места, сложно читать и конфигурировать. С учетом дальнейшего развития логики скриптов и проверки такой подход является ошибочным.
* **Причина ошибки ИИ:**  
  ИИ попытался решить задачу «быстрым путем», поместив всю логику в один файл, нарушив базовый принцип разделения ответственности (**Separation of Concerns**).
* **Исправление:**  
  Проведен глубокий рефакторинг:
  1. Вся вспомогательная логика вынесена в изолированные файлы: `scripts/setup-kuma.js`, `scripts/configure-grafana.sh`, `dashboards/dashboard.json`.
  2. В Go-модуле Dagger остались только оркестрационные вызовы.
  3. Пейлоады передаются в `curl` через безопасный ключ `-d @/tmp/import.json`, что полностью исключило проблемы с экранированием символов.

### Кейс 4. Борьба с кэшированием Dagger: «костыли» с метками времени вместо нативного API

* **Что предложил ИИ:**  
  В процессе тестирования выяснилось, что Dagger кэширует шаги развертывания (BuildKit Cache). При повторном вызове `dagger call deploy-monitoring` или `destroy` Dagger мгновенно возвращал `0.0s CACHED` и не выполнял реальные команды на хосте.  
  В качестве решения ИИ предложил пробрасывать в контейнеры динамическую переменную `WithEnvVariable("CACHE_BUST", time.Now())`, а когда это не помогло (так как кэшировался сам вызов функции на уровне GraphQL-резолвера), ИИ предложил передавать флаг `--nonce=$(date +%s)` в CLI при каждом запуске.
* **Как обнаружена проблема:**  
  Введение новых и ненужных флагов временной метки только для отключения кэширования является четким hardcode и антипаттерном.
* **Причина ошибки ИИ:**  
  ИИ использовал устаревшие паттерны обхода кэша для старых версий Dagger, не зная о появившихся нативных директивах управления кэшем для модулей.
* **Исправление:**  
  После поиска по запросу `dagger как отключить кэширование` была найдена [документация](https://dagger.io/blog/cache-control-for-modules/) с описанной функцией контроля кэша для функций с побочными эффектами (side-effects). В код модуля была добавлена нативная прагма:
  ```go
  // +cache="never"
  func (m *MonitoringStand) DeployMonitoring(...)
  ```
  Это полностью устранило паразитный кэш без изменения сигнатуры вызова команд в CLI.

### Кейс 5. Иллюзия работы `restart-policy` при `docker stop` и защита PID 1 в Linux

* **Что предложил ИИ:**  
  Для реализации бонусного задания (Chaos Testing) ИИ сначала предложил просто вызвать `docker stop mariadb`, утверждая, что контейнер тут же автоматически перезапустится по политике `restart: unless-stopped`.  
  Когда контейнер ожидаемо остался выключенным, ИИ предложил эмулировать падение через вызов `docker exec mariadb kill -s SIGKILL 1`.
* **Как обнаружена проблема:**  
  1. При `docker stop` контейнер не перезапускался вовсе.
  2. При `docker exec mariadb kill -s SIGKILL 1` команда отрабатывала без ошибок, но контейнер продолжал работать как ни в чем не бывало. Тест падал по таймауту 60 секунд.
* **Причина ошибки ИИ:**  
  1. **Специфика Docker Daemon:** ИИ не учел, что при вызове `docker stop` демон взводит флаг `HasBeenManuallyStopped = true`, который **намеренно подавляет** автоматический перезапуск контейнера независимо от политики (`always` или `unless-stopped`).
  2. **Специфика ядра Linux (PID Namespaces):** Процесс PID 1 внутри пространства имен контейнера аппаратно защищен ядром от сигналов `SIGKILL`/`SIGTERM`, если они посылаются процессом изнутри того же пространства имен (что и делает `docker exec`). Сигнал просто молча игнорировался ядром.
* **Исправление:**  
  Вместо заблокированного `SIGKILL` был применен сигнал аппаратной ошибки памяти `SIGSEGV` (Segmentation Fault):
  ```bash
  docker exec mariadb sh -c "kill -SEGV 1"
  ```
  Сигнал `SIGSEGV` не подавляется ядром Linux даже для PID 1. Процесс аварийно завершился (Exit Code `139`), Docker зафиксировал реальный крэш процесса (без флага ручной остановки) и мгновенно перезапустил MariaDB по политике `unless-stopped`. Тест прошел идеально.

## 3. Выводы и рефлексия (Key Takeaways)

1. **Скорость vs Точность:** ИИ незаменим для генерации бойлерплейта (Go-структуры, заготовки Compose-файлов, первичные PromQL-запросы), экономя до 70% времени на старте проекта.
2. **Ограниченность контекста системного уровня:** В вопросах взаимодействия ядра ОС, сигналов Linux (POSIX signals) и низкоуровневых механизмов контейнеризации (PID namespaces, демоны Docker/BuildKit) генеративные модели регулярно предлагают правдоподобно звучащие, но технически нерабочие решения.
3. **Необходимость глубокой верификации:** Ни одна строчка конфигурации безопасности (права доступа, секреты, токены) не должна приниматься на веру. Критически важно сверять предложения ИИ с официальной документацией и валидировать поведение систем на практике в терминале.
